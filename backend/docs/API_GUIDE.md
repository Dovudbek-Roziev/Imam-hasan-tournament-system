# API: списки, обзор и архив

Третий этап backend. Полный машиночитаемый контракт доступен по `GET /api/openapi.json` и в [openapi.json](openapi.json). Исходник — [openapi.js](openapi.js); после изменения выполните `npm run docs:generate`. Файл можно импортировать в Swagger Editor или Postman. Формат описан в [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0.html).

## Списки

`GET /api/teams`, `/api/players`, `/api/matches`, `/api/news` возвращают `data` массивом и добавляют `pagination`. По умолчанию выдаются первые **20** записей; максимум — 100. Старым клиентам нужно добавить переход по страницам, иначе они увидят только первую страницу. Полная турнирная таблица `/api/stats/table` остаётся без пагинации; рейтинги голов и ассистов возвращают до 10 игроков с положительными показателями.

Сообщения об ошибках по умолчанию русские. Чтобы получить кыргызский текст ошибки, отправляйте заголовок `Accept-Language: ky`. Коды ошибок и структура ответа не меняются.

Логотип команды можно передать как HTTP/HTTPS URL либо загрузить файл JPEG, PNG или WebP размером до 2 МБ: отправьте бинарное тело `POST /api/media` с токеном администратора и соответствующим `Content-Type`. В ответе приходит путь `/api/media/{id}`, который можно сохранить в `logo`; `GET /api/media/{id}` публично отдаёт само изображение. `DELETE /api/media/{id}` доступен администратору и удаляет только неиспользуемые изображения; панель очищает старый логотип после сохранения команды.

```json
{
  "success": true,
  "data": [],
  "pagination": { "page": 1, "limit": 20, "total": 0, "pages": 0, "hasNext": false }
}
```

Общие параметры: `page`, `limit`, `sort`. Страницы начинаются с 1. Смещение `(page - 1) × limit` ограничено 100000. Страница за последней возвращает пустой массив и действительное общее количество. Для равных значений сортировки используется ID.

| Ресурс | Фильтры | sort | По умолчанию |
| --- | --- | --- | --- |
| teams | search — название | name, -name, -points | name |
| players | search — имя; team — ID команды | name, -name, number, -goals, -assists | name |
| matches | team — любой участник; status; from; to | date, -date | date |
| news | search — заголовок; from; to | date, -date, title | -date |

Поиск буквальный, без учёта регистра: `.*` ищет эти символы, а не произвольный текст. Строка поиска после удаления краевых пробелов должна содержать 1–100 символов. Значения query передавайте через URLSearchParams или Axios `params`, чтобы русские символы правильно кодировались.

`from` и `to` — календарные даты `YYYY-MM-DD`, обе границы включены. Для матчей это даты расписания; для новостей — дни UTC. Сортировка матчей дополнительно учитывает `time`. Неизвестные параметры, повторённые значения, вложенные объекты, неверные даты, ID и лимиты возвращают 400. Параметры фильтров не передаются в MongoDB напрямую. Страница и её количество вычисляются через один [MongoDB $facet](https://www.mongodb.com/docs/manual/reference/operator/aggregation/facet/).

Примеры:

```text
GET /api/teams?search=Ош&page=1&limit=20
GET /api/players?team=<ID>&sort=-goals
GET /api/matches?team=<ID>&status=Завершён&from=2026-10-01&to=2026-10-31
GET /api/news?sort=-date&page=2&limit=10
```

Новости содержат обязательные `title` и `content` на русском языке и необязательные `titleKy` и `contentKy` на кыргызском. Кыргызские поля можно пропустить при создании или обновить отдельно; клиенты показывают русскую версию, если перевод отсутствует.

```json
{
  "title": "Турнир начинается",
  "content": "Первый матч состоится в субботу.",
  "titleKy": "Турнир башталат",
  "contentKy": "Биринчи беттеш ишемби күнү өтөт."
}
```

Связанные команды и игроки в GET-ответах раскрываются в объекты с `_id` и именем. POST/PUT могут возвращать эти ссылки строковыми ID. Формы записи должны извлекать ID, а не пересылать раскрытые объекты. Поля `startsAt`, `timeZone`, `_id`, `__v`, timestamps и вычисленная статистика не принимаются в теле записи. Для PUT матча `__v` нужно передать как `version`.

## Dashboard

`GET /api/stats/dashboard` требует JWT администратора. Ответ не кешируется. Связанные коллекции читаются внутри одной транзакции со snapshot read concern.

```json
{
  "success": true,
  "data": {
    "generatedAt": "2026-10-17T10:00:00.000Z",
    "timeZone": "Asia/Bishkek",
    "teams": 4,
    "players": 8,
    "news": 2,
    "matches": {
      "total": 3,
      "scheduled": 1,
      "live": 1,
      "finished": 1,
      "cancelled": 0,
      "goals": 1,
      "incompleteProtocols": 0
    },
    "upcoming": []
  }
}
```

`goals` — сумма счёта только завершённых матчей, включая автоголы. `incompleteProtocols` — число завершённых матчей без полного протокола. `upcoming` — до пяти запланированных матчей с началом не раньше `generatedAt`, по возрастанию абсолютного времени; старые просроченные записи и live-матчи туда не входят. Пустая база возвращает нули и пустой список. Dashboard показывает фактические счётчики статусов; сервер не меняет статус автоматически по часам.

## Время турнира

Место проведения согласовано: **Ош, Кыргызстан**. Значение по умолчанию — `TOURNAMENT_TIME_ZONE=Asia/Bishkek`; для Оша в 2026 году это [UTC+6](https://www.timeanddate.com/time/zone/kyrgyzstan/osh).

При создании сервер сохраняет IANA-пояс в `timeZone`. Каждый GET/POST/PUT ответа матча также содержит рассчитанный `startsAt` в UTC. Пример: `date=2026-10-17`, `time=18:30` → `startsAt=2026-10-17T12:30:00.000Z`. Мобильный countdown должен использовать `new Date(startsAt)`, а не собирать дату в часовом поясе телефона.

Изменение env влияет только на новые матчи. Уже сохранённый пояс нельзя менять через API. Старые записи без `timeZone` интерпретируются в `Asia/Bishkek`, согласно выбранному месту турнира. Некорректные старые даты дают `startsAt: null`; интерфейс должен показывать отсутствие корректного времени. Новые неоднозначные или несуществующие локальные часы при переходе летнего времени отклоняются. Вычисление использует базу часовых поясов среды Node.js через [Intl.DateTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat); Node.js и MongoDB нужно обновлять при изменении правил IANA.

## Демонстрационные данные

Команда `demo:seed` не читает рабочий `.env` и не использует `MONGO_URI`. Нужен отдельно переданный `DEMO_MONGO_URI`, имя базы должно оканчиваться на `_demo`. Коллекции команд, игроков, матчей, новостей и пользователей должны быть пустыми. Повторный запуск возвращает ошибку и сохраняет существующие данные. Вся загрузка выполняется в одной транзакции.

Пример для уже настроенного локального replica set:

```powershell
cd backend
$env:DEMO_MONGO_URI = 'mongodb://127.0.0.1:27017/imam_hasan_demo?replicaSet=rs0'
npm run demo:seed
Remove-Item Env:DEMO_MONGO_URI
```

Создаются четыре вымышленные команды, восемь игроков, три матча (завершённый с голом/ассистом, live, следующий день) и две русские новости. Дата привязана к текущему дню в часовом поясе турнира. Статистика рассчитывается сервисом проекта; общего демонстрационного пароля нет.

Для просмотра демобазы настройте backend на её URI и отдельно выполните `npm run admin:create` **после** seed. Команда не очищает базу, не создаёт администратора и не заменяет действующие результаты. Во время разработки данные создавались только во временной тестовой MongoDB.

## Подготовка архива сезона

`GET /api/stats/archive` с JWT администратора скачивает `imam-hasan-archive.json`. В одном снимке сохраняются команды, игроки, матчи, новости, время экспорта, часовой пояс и `schemaVersion: 1`. Пользователи, пароли и токены исключены. Счётчики в экспорте заново рассчитываются из завершённых матчей без изменения рабочей базы. Повреждённые протоколы возвращают 409; экспорт ограничен 10000 записями на коллекцию.

Это переносимый снимок истории для небольшого турнира. Он не заменяет резервное копирование MongoDB: учётные записи и индексы в JSON не входят. Автоматический импорт, переключение сезонов, трансферы между сезонами и сброс текущего турнира пока не реализованы. До добавления сезонов историю нельзя очищать ради нового турнира. Следующая архитектурная итерация потребует сущности Season, сезонных составов, привязки матчей к сезону и блокировки статистики на уровне сезона.

## Ограничения и проверка

Поиск по подстроке и полный пересчёт рассчитаны на небольшой турнир. Индексы дат матчей, новостей и состава команды объявлены в моделях; в production `autoIndex` отключён, поэтому применение индексов нужно включить в процедуру размещения. API возвращает `requestId` при ошибках. Полный список кодов и структуры — в OpenAPI и [правилах турнира](TOURNAMENT_RULES.md).

Проверки: `npm run docs:generate`, `npm run check`, `npm run lint`, `npm test`. Тесты проверяют HTTP-фильтры, страницы, границы дат, защиту dashboard/архива, преобразование времени Оша, демоданные, откат транзакций, соответствие JSON спецификации и разрешимость её ссылок. Веб-админка и мобильные вкладки используют этот контракт; запуск backend и MongoDB для клиентских проверок выполняется отдельно.
