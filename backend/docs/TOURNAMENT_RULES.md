# Правила матчей и статистики

Контракт второго и третьего этапов. Система пока обслуживает один турнир в городе Ош, Кыргызстан. API, время, демоданные и подготовка архива описаны в [руководстве](API_GUIDE.md). Переключение сезонов и автоматическое определение победителя при полном равенстве спортивных показателей пока не реализованы.

## Официальные показатели

Таблица, бомбардиры, ассисты и карточки учитывают только матчи со статусом `Завершён`. Победа даёт 3 очка, ничья — 1, поражение — 0. При возврате матча в статус `Идёт` его вклад удаляется из официальных показателей. При повторном завершении вклад восстанавливается.

Таблица сортируется по очкам, разнице мячей и забитым мячам по убыванию, затем по имени и ID для стабильного отображения. Имя и ID не заменяют спортивный регламент определения победителя. Бомбардиры и ассистенты — первые 10 игроков с положительным показателем; равенство разрешается стабильной сортировкой по имени и ID.

Каждое создание, изменение или удаление матча заново рассчитывает показатели всех команд и игроков. Поэтому смена команды матча, удаление последнего события и исправление автора гола очищают прежние значения. Ручное изменение счётчиков через API запрещено.

## Статусы и протокол

| Поле | Допустимые значения |
| --- | --- |
| status | Запланирован, Идёт, Завершён, Отменён |
| events[].type | Гол, Автогол, Жёлтая карточка, Красная карточка |
| protocolComplete | false — неполный протокол; true — полный |

Для запланированного или отменённого матча счёт должен быть 0:0, события — пустыми. При переводе сыгранного матча в такой статус нужно передать обнулённый счёт и пустой массив событий тем же запросом.

По умолчанию протокол неполный: количество записанных голов каждой команды не может превышать её счёт. Полный протокол требует точного совпадения голов и счёта. Неполный протокол позволяет внести известный результат до заполнения авторов голов. Командная таблица при этом учитывает весь счёт, персональная статистика — только известные события. Будущие интерфейсы должны явно показывать неполный протокол.

Игрок события должен существовать и принадлежать одной из команд матча. Сервер сам сохраняет `events[].team`; клиент не может подменить это поле. `assist` — ID другого игрока той же команды, допускается только у события `Гол`. Автогол добавляет мяч сопернику, не увеличивает личные голы автора и не допускает ассистента. Карточки считаются по событиям; автоматические дисквалификации и преобразование двух жёлтых в красную пока не реализованы.

## Формат запросов

Запись требует JWT администратора. Неизвестные поля, операторы MongoDB, счётчики статистики и служебные поля возвращают 400. Числа передаются JSON-числами, а не строками; идентификаторы — строками из 24 шестнадцатеричных символов.

| Ресурс | Изменяемые поля |
| --- | --- |
| Команда | name, logo |
| Игрок | name, team, number |
| Матч | homeTeam, awayTeam, homeScore, awayScore, date, time, stadium, status, events, protocolComplete |
| Событие | minute, player, type, assist |
| Новость | title, content |

Обновление матча дополнительно требует `version`, равную `__v` из последнего ответа API. Устаревшая версия возвращает 409 `VERSION_CONFLICT`; клиент должен загрузить свежий матч и предложить повторное редактирование. При передаче массива `events` он заменяется полностью: возвращаемые `_id` и `team` событий нужно исключить из тела запроса.

Пример `POST /api/matches` (ID заменить на существующие):

```json
{
  "homeTeam": "000000000000000000000001",
  "awayTeam": "000000000000000000000002",
  "date": "2026-10-25",
  "time": "18:30",
  "stadium": "Основной стадион",
  "status": "Запланирован"
}
```

Пример `PUT /api/matches/:id` для версии 0:

```json
{
  "version": 0,
  "status": "Завершён",
  "homeScore": 1,
  "awayScore": 0,
  "protocolComplete": true,
  "events": [
    {
      "minute": 23,
      "player": "000000000000000000000003",
      "type": "Гол",
      "assist": "000000000000000000000004"
    }
  ]
}
```

Для удаления рекомендуется `DELETE /api/matches/:id?version=1` с актуальной версией. Без query-параметра удаление допускается без проверки версии. Остальные обновления принимают частичный набор разрешённых полей.

## Границы данных

- Счёт: целые числа от 0 до 999; минуты: от 0 до 180; максимум 500 событий.
- Дата: существующая календарная дата `YYYY-MM-DD`; время: `HH:mm` в 24-часовом формате. Дата хранится как полночь UTC, время отдельно. Для countdown API возвращает абсолютное время `startsAt` и сохранённый `timeZone`; по умолчанию используется `Asia/Bishkek` для Оша.
- Название команды и имя игрока: до 100 символов; стадион: до 150.
- Номер игрока: целое 1–99 либо null; непустой номер уникален в команде.
- Логотип: пустая строка либо HTTP/HTTPS URL без логина/пароля, до 2048 символов.
- Заголовок новости: до 200 символов; содержание: до 20000. Дату публикации задаёт сервер.

Это технические ограничения MVP, а не утверждённый спортивный регламент. Пользовательский контент вводится по-русски; имена людей, названия команд и URL не проходят автоматическую проверку языка.

## История и транзакции

Команду нельзя удалить, если у неё есть игроки или матчи. Игрока нельзя удалить или перевести, если он указан автором события либо ассистентом в любом матче. Переименование и смена номера допустимы. Полноценная история переходов между сезонами пока не реализована.

Все изменения команд, игроков и матчей проходят через общую запись блокировки турнира внутри MongoDB-транзакции. Матч и производные показатели сохраняются вместе; при ошибке все изменения транзакции отменяются. Конкурентные операции повторяются драйвером, а версии матчей защищают от перезаписи устаревшей формы. Документы загружаются заново внутри каждого повтора.

Требуется replica set или Atlas: [standalone MongoDB не поддерживает транзакции](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/). Полный пересчёт и общая блокировка подходят небольшому турниру; для нескольких крупных турниров понадобятся отдельные блокировки по турниру и иной объём пересчёта. Прямые изменения коллекций обходят эти гарантии — запись должна идти через сервисы API.

## Существующая база и восстановление показателей

Для совместимости принимаются прежние `scheduled/live/finished/cancelled` и `goal/own_goal/yellow_card/red_card`. Новые записи и отредактированные матчи сохраняют русские значения; API показывает русские значения и для старых записей. Сами старые документы автоматически массово не переписываются.

После обновления существующей базы проверьте старые протоколы и выполните из папки backend:

```powershell
npm run stats:rebuild
```

Команда подключается к MONGO_URI из .env и атомарно пересчитывает все командные и персональные счётчики, включая обнуление прежних значений. Старый статус `finished` тоже учитывается. Повторный запуск даёт тот же результат. До первого пересчёта или изменения матча ранее сохранённые счётчики могут оставаться устаревшими.

Отсутствующие команды/игроки, неправильная принадлежность событий или несогласованный счёт приводят к `INVALID_MATCH_HISTORY` (409 в API) и откату. Некорректная история не пропускается молча: сначала нужно исправить исходный матч. Команда не восстанавливает удалённые сущности и не дополняет неизвестные события. В ходе второго этапа пользовательская внешняя база не изменялась; пересчёт проверен только на изолированной тестовой базе.

## Плей-офф / Playoff format

После того как все матчи лиги завершены или отменены, четыре лучшие команды выходят в плей-офф: 1-е место играет с 4-м, 2-е — с 3-м. Победители полуфиналов встречаются в финале; проигравшие могут сыграть отдельный матч за третье место. Для определения места в лиге используются очки, разница голов и забитые голы; при полном равенстве применяется стабильный технический порядок по названию и ID команды.

В матче на выбывание ничья после основного счёта требует результата серии пенальти. Администратор выбирает этап матча, а сервер проверяет допустимые пары и участников следующего этапа. Таблица лиги учитывает только матчи этапа «Лига»; голы, передачи и карточки игроков считаются по всем завершённым этапам. После создания плей-офф результаты и состав матчей лиги заблокированы, пока не удалены зависимые матчи плей-офф.

Мобильная схема показывает предполагаемые пары по текущей таблице до начала плей-офф и реальные результаты после их внесения. Формат и спортивные критерии остаются правилами организатора турнира; система обеспечивает их техническое применение.

Once every league match is finished or cancelled, the top four teams enter the playoffs: 1st plays 4th and 2nd plays 3rd. The semifinal winners meet in the final; the two losing teams can play a separate third-place match. League ranking uses points, goal difference, and goals scored; a complete tie is resolved by a stable technical order based on team name and ID.

A knockout draw after regular time requires a penalty-shootout score. The administrator selects each match stage, and the server validates the allowed semifinal pairings and the teams advancing to the next stage. League standings include only matches marked “League”; player goals, assists, and cards include every finished stage. Once a playoff match exists, league fixtures and results are locked until dependent playoff matches are removed.

Before playoffs begin, the mobile bracket previews pairings from the current standings; after results are entered, it displays the actual outcomes. The tournament organizer owns the final sporting regulations, while the system enforces the configured format.
